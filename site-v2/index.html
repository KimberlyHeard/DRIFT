AI can write a driver in minutes. Checking it against the datasheet is the hard part.

Every chip ships with a datasheet: dozens of pages of registers, bit fields, byte order, timing and calibration. Turning it into a driver is careful manual translation, usually done before the board exists. AI assistants can produce that code rapidly; teams still need to verify the behavior against the source.

Today

Translate by hand, find out on hardware

Mistakes in byte order, timing or calibration surface on a physical bench, where they are slow to reproduce and hard to explain.

With AI assistants

Generated code still needs checking

A generated driver can compile and look right while misreading the sensor. Reviewers need more than the code and the model's confidence.

With DRIFT

Behavior checked against reviewed facts

Approved facts, independent expectations, a deterministic virtual sensor and a trace whose fact-tagged steps link to cited source pages.

Who it is for

  • Firmware engineers bringing up a new sensor before boards arrive.
  • Hardware startups without a dedicated validation team.
  • Teams adopting AI assistants who need an audit trail for generated code.
  • Reviewers who need to show why a driver can be trusted.

How it works

DEFDriver: the code that lets a processor talk to a chip over a bus.
DEFVirtual sensor: a deterministic Python model of the chip's selected registers and conversion timing, with an integer microsecond clock. Ordinary code, not an AI imitating a sensor.
WHYWhy not just ask for a driver? DRIFT returns code plus reviewed sources, independent expectations and reproducible failing cases that show when the code is wrong.

A defect the checks found on their own

Separately from the seeded defect, Bob's first TMP117 virtual device lost the finished temperature when a configuration read cleared the ready flag. Integration tests caught it. Bob corrected the model; the independent temperature expectations did not change.

Second sensor: Bosch BME280

The TMP117 hands back a finished temperature. The BME280 does not: the driver must read six calibration bytes stored little-endian and signed, assemble a 20-bit raw reading, and run Bosch's integer compensation formula. Different byte order, different conversion semantics, same workflow.

    Limits

    • Two reviewed, device-specific profiles; BME280 is temperature-only forced mode.
    • Software verification against virtual sensors. No electrical waveform model.
    • No physical hardware validation and no measured hardware accuracy.
    • No arbitrary-PDF ingestion; every contract needs a human review.
    • This site replays recorded Python evidence. No measured time savings.
    • Mature drivers exist for both parts; they were chosen because correct behavior is knowable.
